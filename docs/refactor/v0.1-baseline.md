# v0.1 Baseline

## What "v0.1 baseline" means

`v0.1` is the name for the current checked-out state of Agent Workbench,
frozen as a comparison anchor before any structural refactor of the workflow
harness (`run.py`, `core/steps.py`, `core/run_cmds.py`, `eval/runner.py`)
begins. It is not a release tag or a code change — it is a **snapshot of
facts about the repo**: what benchmarks exist, what shape their fixtures are
in, what config/prompt files influence runs, and what the environment looked
like when the snapshot was taken.

## Why we are freezing it before refactoring

Planned v0.2/v0.3/v0.4 work will reorganize the eval/runner/workflow layers.
Without a recorded baseline, it's hard to tell "the benchmark harness
changed behavior" apart from "the benchmark fixtures themselves drifted" or
"this is just a different machine/Python version." The baseline manifest
gives every later change a fixed point to diff against: same benchmark file
hashes, same runner/config hashes, same inventory shape, so any observed
difference in outcomes is more likely attributable to the refactor itself.

## How to capture a baseline

```bash
python3 scripts/capture_v01_baseline.py
```

This writes `baselines/v0.1/baseline_manifest.json` (repo-root-relative, or
pass `--output <path>` to write elsewhere). Pass `--repo-root <path>` to
inspect a different checkout (used by the script's own tests against a fake
temp repo).

The script does not run any workflow, benchmark, or LLM call — it only
inspects the filesystem, git metadata, and the Python/platform environment.
It requires no optional SDKs (no Opik, no cloud tracing, no vendor clients)
and no network access.

## What metadata is captured

- `baseline_id` — `v0.1-<git-commit>` (or `v0.1-no-git` if git metadata is
  unavailable).
- `created_at` — capture timestamp (UTC ISO-8601). This is the only field
  expected to differ between two captures of the same commit.
- `code_version` — git commit SHA and dirty/clean working-tree status.
- `environment` — Python version, platform string, OS, machine arch.
- `benchmark_inventory` — one entry per discovered case under
  `eval/benchmarks/<case>/`, with `story.json` / `hidden_tests.py` presence
  and SHA-256 hashes, and an inferred `difficulty`.
- `eval_report_inventory`, `trace_log_inventory`, `artifact_inventory` —
  file listings (path, existence, count) for `eval/reports/`, `logs/`, and
  `agent-context/`.
- `prompt_config_hashes` / `runner_workflow_config_hashes` — SHA-256 hashes
  of a curated set of files that shape prompts, workflow config, or the
  runner/eval harness itself.
- `notes` — free-text caveats about the capture (see below).

Everything else about the schema (exact keys/nesting) is visible directly in
`baselines/v0.1/baseline_manifest.json` and in
`scripts/capture_v01_baseline.py::build_manifest`.

## Where baseline artifacts are stored

`baselines/v0.1/baseline_manifest.json`, committed to the repo. It is the
frozen v0.1 anchor, not a per-run report — regenerating it against the same
commit should reproduce the same content (other than `created_at`).

Note that `eval/reports/`, `logs/`, and `agent-context/` are **gitignored,
local runtime directories**. The manifest inventories whatever happens to
exist on the machine that ran the capture, and clearly marks the case where
one of these directories doesn't exist at all (`"exists": false`) as
distinct from existing-but-empty (`"file_count": 0`). A baseline captured on
a fresh clone will show `exists: false` for all three — that is expected,
not a bug.

## How future candidate runs should be compared against it

1. Run `python3 scripts/capture_v01_baseline.py --output baselines/<candidate>/baseline_manifest.json`
   on the candidate branch/commit.
2. Diff `benchmark_inventory` and `runner_workflow_config_hashes` /
   `prompt_config_hashes` against the v0.1 manifest to see exactly which
   benchmark fixtures or config/runner files changed.
3. If a refactor is meant to be behavior-preserving, the benchmark file
   hashes should be unchanged; changed runner/workflow hashes are expected
   and just tell you which files moved.
4. For actual eval outcomes (pass/fail, quality scores), continue to use
   `eval/runner.py --compare-to <baseline-report>` — the baseline manifest
   here is about *what was evaluated and with what code*, not about scoring
   a specific run. A future task can wire baseline-manifest awareness into
   the runner's own `--compare-to` flow.

## Known limitations of v0.1 evaluation and tracing

- Benchmarks use a **legacy per-case structure**: exactly one
  `story.json` + `hidden_tests.py` pair per difficulty directory
  (`eval/benchmarks/easy|medium|hard/`). There is no multi-case-per-difficulty
  layout and no newer manifest format yet — the capture script intentionally
  matches this legacy shape rather than inventing a new one.
- `eval/reports/`, `logs/`, and `agent-context/` are local and gitignored, so
  the "inventory" portions of a baseline are only as complete as whatever
  happens to be on the machine that ran the capture — they are not a
  reproducible record of eval history across machines/clones.
- The runner/workflow config hash list in the manifest is **curated, not
  exhaustive** (a handful of files known to shape runner/eval behavior).
  It will miss config surfaces added later unless the list in
  `scripts/capture_v01_baseline.py` is updated.
- No cost/token/runtime metrics are captured here — those live in
  `eval/reports/*.json` from actual runner executions, which this baseline
  only inventories by filename, not by content.

## Known optional-integration hazards

- `core/opik_compat.py` already makes the Opik SDK import optional and
  supplies no-op fallbacks, so a missing `opik` package does not break
  import of anything in `core/` or `eval/`. `core/opik_integration.py`
  guards its `import anthropic` the same way (try/except at import time).
  No eager, unguarded optional-SDK imports were found on the
  `eval/runner.py` → `core.runtime_paths` / `core.runner_models` /
  `eval.result_schema` / `eval.seed_benchmarks` import path used by the
  baseline capture script or its tests.
- `requirements.txt` lists `opik`, `anthropic`, and `google-genai` as
  installed dependencies in this environment; the guards above mean baseline
  capture and the core eval schema tests would still work even if those
  packages were absent, but this has not been verified with them physically
  uninstalled.
