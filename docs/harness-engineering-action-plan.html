Harness Engineering Action Plan for Agent Workbench

Detailed implementation directions for turning the existing local multi-agent runner into a stronger production-grade AI harness: measurable, reproducible, debuggable, guarded, and safe to change.

Source note. The referenced X post links to an X Article titled Harness Engineering: What Every AI Engineer Needs to Know in 2026. X exposed only the post preview without login, but an accessible mirrored article with the same title was available. The action plan below is based on the verified accessible text and the current repository structure. The article's core framing is: do not only ship prompts or models; ship the harness around them: evaluations, test datasets, observability, guardrails, routing, rollback paths, and release controls.

1. Current state of this runner

Agent Workbench already contains many of the right harness primitives. The recommended work is mostly about making those primitives stricter, more machine-readable, and more actionable.

Harness capabilityCurrent implementationWhat to improve
Workflow orchestration run.py executes materialize, intake, task generation, task assignment, execution, QA, and PR review. Make the stage outputs, stage gates, and failure states more formally typed and resumable.
Evaluator loops core/evaluator_optimizer_loops.py runs eval-optimizer loops for planning, assignment, implementation, and QA. Replace string-based pass/fail detection with JSON schemas, score dimensions, and machine-readable required fixes.
Artifacts Canonical artifacts live under agent-context/<change-id>/, with validation in core/artifact_utils.py. Add a run manifest and reproduction manifest tying together artifacts, events, prompts, repo state, and model state.
Observability Events, Opik tracing, LLM call metadata, token estimates, and GUI trace bridge exist. Use those traces as evaluation inputs and publish trajectory summaries in reports.
Runner abstraction core/run_cmds.py, core/runner_models.py, and runner-specific materialized assets support Claude, Codex, Copilot, Gemini, and OpenAI-compatible backends. Normalize all runner outputs into the same typed telemetry and policy model.
Tool guardrails OpenAI-compatible local tool runtime has allowed roots, typed artifact writers, forbidden write paths, network command blocking, output truncation, and max tool steps. Apply equivalent policy reporting across all runner types and make policy violations first-class eval data.
Escalation core/user_escalation.py and core/escalation_mcp_server.py support blocking user questions through the GUI/TTY. Score escalation behavior: missing escalation when required, unnecessary escalation, unresolved escalation, and escalation latency.
Evals eval/runner.py, eval/agent_runner.py, and eval/agent_metrics.py support hidden-test workflow benchmarks and standalone agent metrics. Add trajectory and harness-health metrics beyond final test pass/fail.
Prompt/materialization versioning core/materialize.py records hashes and generated runner assets. Attach materialization hashes and prompt lineage to every run, eval result, and reproduction bundle.

2. North-star harness properties

A production-grade AI runner should make every meaningful behavior change answerable with evidence. The target properties are:

  1. Measurable: Every workflow produces typed scores, not just logs and prose.
  2. Reproducible: Any failed stage can be rerun from a manifest without reconstructing context manually.
  3. Trajectory-aware: The harness evaluates the path the agent took: tool calls, commands, edits, tests, escalations, and retries.
  4. Guarded: The runner enforces budgets, permissions, diff scope, and release gates before producing or merging changes.
  5. Comparable: Runs can be compared across model, prompt, runner, materialization, and configuration changes.
  6. Actionable: Failure reports identify the responsible stage, missing evidence, likely root cause, and next command to run.

4. Add typed evaluator contracts

The current evaluator loops stop early when "PASS" appears in the evaluator output. That is fragile: a sentence such as “does not PASS” can accidentally pass, and the harness cannot reliably aggregate score details.

4.1 Add a canonical evaluator result schema

Create a new module, for example core/evaluator_result.py, with a schema like this:

{
  "schema_version": "evaluator-result/v1",
  "status": "PASS | FAIL | BLOCKED",
  "overall_score": 0.0,
  "dimensions": [
    {
      "id": "acceptance_criteria_coverage",
      "score": 0.0,
      "severity": "critical | major | minor",
      "summary": "What was evaluated",
      "evidence_refs": ["agent-context/.../tasks.yaml"],
      "required_fixes": ["Add explicit AC-2 task coverage"]
    }
  ],
  "blockers": [
    {
      "id": "missing_human_decision",
      "summary": "A product decision is required",
      "requires_escalation": true
    }
  ],
  "regression_risk": "low | medium | high",
  "summary": "Short human-readable evaluation summary"
}

4.2 Parser and compatibility behavior

  • Add parse_evaluator_result(text: str) -> EvaluatorResult.
  • Accept fenced JSON, raw JSON, and legacy text.
  • For legacy text, map exact normalized PASS to pass, exact normalized FAIL to fail, and all other content to FAIL with raw_response.
  • Never use substring detection for pass/fail.
  • Persist both raw evaluator output and parsed evaluator result.

4.3 Update loop logic

Modify core/evaluator_optimizer_loops.py:

  • In run_uow_eval_loop, replace passed = "PASS" in evaluator_out with parsed.status == "PASS".
  • In run_eval_optimizer_loop, use the same parser.
  • Emit loop events with overall_score, dimension_scores, blocker_count, and critical_failure_count.
  • Write eval_impl_N.json using the typed schema, not an ad hoc fallback.

4.4 Update evaluator prompts

Evaluator agents should be required to output only JSON in this schema. Relevant source prompt directories include agent-definition-source and materialized runner assets. Because this repo intentionally avoids automatic prompt mutation during workflow runs, update the canonical source prompts and then run materialization explicitly.

4.5 Acceptance criteria

  • String outputs containing “PASS” inside longer text no longer pass unless the parsed status is exactly PASS.
  • All evaluator-loop events include typed status and score fields.
  • Existing tests in tests/test_evaluator_optimizer_loops.py are updated to cover typed pass, typed fail, malformed JSON, and legacy exact PASS.

5. Add trajectory-level evaluation

Agentic systems are not adequately evaluated by final output alone. The harness should score whether the agent took a safe, efficient, evidence-backed path.

5.1 Define a trajectory summary artifact

Create agent-context/<change-id>/summary/trajectory.json at the end of each run and, for finer debugging, agent-context/<change-id>/execution/<uow-id>/trajectory.json for each UoW.

Suggested fields:

{
  "schema_version": "trajectory/v1",
  "change_id": "ABC-123",
  "stage": "execution",
  "uow_id": "uow-1",
  "runner": "claude",
  "model": "...",
  "tool_calls": {
    "total": 18,
    "by_name": {"read_file": 5, "write_file": 2, "run_shell": 3}
  },
  "commands": [
    {"command": "pytest tests/test_x.py", "cwd": "...", "returncode": 0, "duration_ms": 1200}
  ],
  "files_changed": ["src/example.py", "tests/test_example.py"],
  "tests_observed": {
    "ran": true,
    "commands": ["pytest tests/test_example.py"],
    "failures": 0
  },
  "escalations": {
    "requested": 0,
    "resolved": 0,
    "unresolved": 0
  },
  "policy_violations": [],
  "retry_count": 0,
  "duration_ms": 30000,
  "tokens_estimated": {"input": 12000, "output": 2000}
}

5.2 Build trajectory summaries from existing events

Most data is already emitted through server/events.py and LLM-call events in core/run_cmds.py. Add a summarizer near run.py's existing _summarize_event_rows and _write_run_metrics helpers, or create core/trajectory.py.

5.3 Score trajectories in evals

Extend eval/agent_metrics.py and eval/runner.py with trajectory metrics:

  • Evidence discipline: did the agent inspect relevant files before editing?
  • Test discipline: did the agent run targeted tests or explain why not?
  • Scope discipline: were changed files related to assigned UoWs?
  • Escalation discipline: did the agent escalate only blocking decisions?
  • Retry health: did the loop converge quickly or churn?
  • Policy health: were there denied writes, network attempts, forbidden shell commands, or max-tool-step breaches?

5.4 Acceptance criteria

  • Every workflow run writes summary/trajectory.json.
  • Every UoW writes a trajectory artifact when execution starts.
  • Eval reports include trajectory scores alongside hidden-test results.
  • GUI and JSON reports can display top trajectory warnings.

6. Add failure reproduction bundles

A good harness makes failure reproduction fast. When a workflow fails, engineers should not have to infer which prompt, model, branch, artifact, config, or event log was involved.

6.1 Add a reproduction manifest

On failure and on success, write agent-context/<change-id>/summary/repro_manifest.json. On failure, also print the path in the terminal and GUI event log.

{
  "schema_version": "repro-manifest/v1",
  "change_id": "ABC-123",
  "status": "failed",
  "failed_stage": "execution",
  "failed_uow_id": "uow-2",
  "repo": {
    "path": "/repo",
    "head_sha": "...",
    "branch": "feature/abc-123",
    "dirty_status": "...",
    "diff_stat": "..."
  },
  "runner": {
    "default_runner": "claude",
    "default_model": "...",
    "per_agent_models": {"qa-evaluator": {"runner": "gemini", "model": "..."}}
  },
  "materialization": {
    "metadata_files": [".claude/.materialization.json", ".openai-compat/.materialization.json"],
    "content_hashes": {}
  },
  "artifacts": {
    "story": "agent-context/ABC-123/intake/story.yaml",
    "tasks": "agent-context/ABC-123/planning/tasks.yaml",
    "assignments": "agent-context/ABC-123/planning/assignments.json",
    "events": "agent-context/ABC-123/summary/events.jsonl",
    "run_metrics": "agent-context/ABC-123/summary/run_metrics.json"
  },
  "rerun_commands": {
    "full_workflow": "python3 run.py --repo /repo --manual-story-file ... --change-id ABC-123 --runner claude",
    "hidden_tests": "python3 eval/runner.py --benchmark ...",
    "failed_stage_debug": "python3 scripts/replay_stage.py --manifest ... --stage execution --uow-id uow-2"
  }
}

6.2 Implement minimal replay before full deterministic replay

Do not try to make every external LLM call deterministic at first. Start with a high-value reproducibility bundle that captures enough state to rerun manually. Later, use cassette recording and hermetic mode to replay subprocess I/O.

6.3 Suggested implementation files

  • run.py: write manifest in success and exception paths near _write_workflow_status and _write_run_metrics.
  • server/runner_proc.py: surface manifest path in job failure summaries.
  • server/events.py: emit repro.manifest_written.
  • eval/runner.py: copy manifest into benchmark reports.

6.4 Acceptance criteria

  • Every failed workflow has a manifest even if failure occurs mid-stage.
  • The manifest includes repo SHA, branch, dirty status, runner/model, materialization hashes, event log path, failed stage, failed UoW if known, and rerun commands.
  • Tests cover manifest creation on success and on exception.

7. Isolate parallel UoW execution

run.py can execute multiple UoWs in parallel via ThreadPoolExecutor. If those UoWs operate in the same working tree, agents can race on files, tests, generated artifacts, and git state.

7.1 Add a workspace strategy

Introduce a configurable execution workspace mode:

  • shared: current behavior, allowed only for sequential batches or explicitly trusted runs.
  • worktree: create one git worktree per parallel UoW.
  • copy: fallback for repos where worktrees are unavailable.

7.2 Worktree flow

  1. Before a parallel batch, ensure the base repo is clean enough for branching or record its dirty state.
  2. Create worktrees under a per-run temp directory, such as agent-context/<change-id>/workspaces/<uow-id> or a runtime temp root.
  3. Run run_uow_eval_loop with that UoW-specific repo path.
  4. After each UoW passes, collect a patch with git diff.
  5. Apply patches to the primary repo sequentially in batch order.
  6. If patches conflict, emit a typed merge conflict artifact and escalate to a resolver stage or fail the batch with actionable evidence.
  7. Clean up worktrees unless debug retention is enabled.

7.3 Suggested implementation files

  • core/repo_prep.py: add worktree helpers: create, remove, patch export, patch apply.
  • run.py: modify execution-stage parallel branch to allocate per-UoW repo paths.
  • core/steps.py: ensure prompts and artifact references distinguish target repo path from artifact root.
  • tests/test_repo_prep.py and a new tests/test_parallel_workspaces.py: cover worktree creation and patch conflict behavior.

7.4 Acceptance criteria

  • Parallel UoWs never write to the same target repo path.
  • Each UoW records its workspace path and patch path in its trajectory artifact.
  • Conflicting patches fail with a clear artifact, not silent corruption.

8. Enforce budgets and circuit breakers

The runner already captures token estimates, costs, latency, retries, and tool counts. Turn those observations into controls.

8.1 Add budget configuration

Extend server/config.py and CLI arguments in run.py with a budget block:

{
  "budgets": {
    "run": {
      "max_wall_time_seconds": 7200,
      "max_estimated_tokens": 1000000,
      "max_cost_usd": 20.0
    },
    "stage": {
      "max_iterations": 3,
      "max_retries": 5,
      "max_duration_seconds": 1800
    },
    "uow": {
      "max_changed_files": 25,
      "max_diff_lines": 1500,
      "max_tool_steps": 80,
      "max_policy_violations": 0
    }
  }
}

8.2 Enforcement points

  • core/run_cmds.py: enforce per-agent tool step, retry, and command timeout budgets across all runner transports where possible.
  • run.py: enforce run and stage wall-clock budgets between stages and loop iterations.
  • core/evaluator_optimizer_loops.py: stop loops on budget exhaustion and emit status: BLOCKED or status: BUDGET_EXHAUSTED.
  • core/check_gates.py: enforce changed-file and diff-size limits before PR review.

8.3 Budget events

Emit explicit events such as budget.warning, budget.exceeded, and budget.snapshot. Include budget type, current value, limit, stage, UoW, runner, and model.

8.4 Acceptance criteria

  • Budget exhaustion produces a typed failure reason in workflow status and run metrics.
  • Budget events are visible in the GUI event stream.
  • Tests verify that budget limits stop loops deterministically.

9. Add release gates and rollback controls

The article emphasizes release controls and rollback paths. For this runner, the natural point is immediately before PR creation/review.

9.1 Final release gate artifact

Create agent-context/<change-id>/summary/release_gate.json:

{
  "schema_version": "release-gate/v1",
  "status": "PASS | FAIL | WARNING",
  "checks": [
    {"id": "qa_report_passed", "status": "PASS", "evidence_refs": ["qa/qa_report.yaml"]},
    {"id": "hidden_tests_passed", "status": "PASS", "evidence_refs": []},
    {"id": "diff_scope", "status": "PASS", "changed_files": 8, "diff_lines": 300},
    {"id": "critical_pr_findings", "status": "PASS", "count": 0},
    {"id": "rollback_notes", "status": "PASS", "evidence_refs": ["summary/rollback_plan.html"]}
  ],
  "blocking_failures": [],
  "warnings": []
}

9.2 Rollback plan

Generate a small rollback plan for every non-evaluation run. Because global instructions prefer HTML for new docs, use summary/rollback_plan.html. Include:

  • Files changed.
  • Database migrations or config changes, if any.
  • How to revert the branch or patch.
  • Known runtime toggles or feature flags.
  • Validation commands to run after rollback.

9.3 Suggested implementation files

  • core/check_gates.py: add release gate check functions.
  • core/run_gates.py: orchestrate gate execution.
  • run.py: call final gates before steps.step_pr_review.
  • server/evaluate.py and GUI routes: display release-gate status in run detail pages.

9.4 Acceptance criteria

  • PR review/creation is skipped or blocked when critical release gates fail.
  • Gate failures include evidence references and suggested remediation.
  • Evaluation runs can opt into gates without creating PRs.

10. Attach prompt/model/materialization lineage to every run

The harness should make it easy to answer: “Did this regression come from the model, prompt, tool runtime, or target repo?”

10.1 Run lineage artifact

Create agent-context/<change-id>/summary/run_lineage.json with:

  • Runner name and model for each agent role.
  • Prompt source path and prompt hash for each agent role.
  • Materialization metadata file paths and content hashes.
  • Runner code version: git SHA of this harness repository.
  • Target repo SHA and branch.
  • Configuration file path and hash.
  • OpenAI-compatible endpoint identity where safe to record.

10.2 Integrate lineage into eval reports

Extend eval/result_schema.py and reports generated by eval/runner.py so every benchmark result includes lineage. Then add comparison grouping by:

  • model
  • runner
  • prompt hash
  • materialization hash
  • target repo SHA

10.3 Acceptance criteria

  • Every run has a lineage artifact.
  • Eval reports include lineage for each trial.
  • A baseline-vs-candidate comparison can attribute behavior changes to model/prompt/harness changes when only one axis changed.

11. Make failure reports guide fixes

A strong harness does not only say “failed.” It says what failed, why it matters, where the evidence is, and what to do next.

11.1 Failure diagnosis artifact

Create agent-context/<change-id>/summary/failure_diagnosis.json when a workflow fails or when release gates fail:

{
  "schema_version": "failure-diagnosis/v1",
  "primary_failure": {
    "stage": "qa",
    "uow_id": null,
    "category": "test_failure | evaluator_failure | budget_exhausted | policy_violation | runner_error | artifact_invalid",
    "summary": "QA evaluator found missing AC-3 evidence"
  },
  "evidence_refs": ["qa/qa_report.yaml", "summary/events.jsonl"],
  "likely_root_causes": [
    {"confidence": 0.8, "summary": "Implementation report did not reference AC-3 tests"}
  ],
  "recommended_next_actions": [
    "Open qa/qa_report.yaml and inspect missing AC evidence",
    "Rerun failed UoW with the repro manifest command",
    "Add a hidden test for AC-3 if missing"
  ]
}

11.2 Human-readable HTML report

Also generate summary/failure_report.html for easy review in the GUI or browser. It should link to artifacts, display timeline snippets, show score dimensions, and include copy-paste rerun commands.

11.3 Acceptance criteria

  • Workflow failures produce both JSON and HTML failure reports.
  • The reports include stage, category, evidence, and next actions.
  • Server job summaries link to the report when available.

12. Test plan

Use the existing test suite style and add targeted tests per feature.

FeatureSuggested tests
Typed evaluator contracts Extend tests/test_evaluator_optimizer_loops.py for typed PASS/FAIL/BLOCKED, malformed JSON fallback, exact legacy PASS, and substring false positives.
Trajectory summary Add tests that feed synthetic event rows into the summarizer and verify commands, tool calls, tests, policy violations, and escalation counts.

Workspace isolation Use temporary git repos to verify worktree creation, patch export/apply, cleanup, and conflict artifacts.

13. Suggested implementation sequence

  1. Typed evaluator parser first. It is small, high leverage, and reduces false pass/fail behavior immediately.
  2. Persist typed evaluator artifacts. Make the loop outputs reliable before adding dashboards or advanced metrics.
  3. Add run lineage and repro manifest. This gives immediate operational value and supports every later feature.
  4. Add trajectory summary from existing events. Start with what is already emitted; do not over-instrument initially.
  5. Extend eval metrics with trajectory scores. Use simple deterministic scoring first, then add richer evaluator-assisted scoring later.
  6. Add budget enforcement. Begin with hard limits on loop iterations, wall time, tool steps, and diff size.
  7. Add release gates. Block PR review/creation when critical checks fail.
  8. Isolate parallel UoWs. This is high value but touches execution flow and git behavior, so implement after manifest/trajectory instrumentation can debug it.
Expected result. After these changes, Agent Workbench will be able to answer, for every run: what was attempted, what changed, which evidence was gathered, which gates passed, where behavior regressed, how to reproduce the failure, and whether the change is safe to release.
